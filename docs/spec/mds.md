# mds 仕様

## 結果を一文で

`mds` という1つの CLI を入れると、Markdown 文書が自分で宣言する YAML スキーマに従って書かれているかを機械検証でき、スキーマが宣言した抽出規則に沿って構造（AST）と値（values）を取り出せる。これにより LLM が書く Markdown の書式を文書単位で厳格に固定できる。ADR は最初の適用例である。

## 用語

- **スキーマ**: 文書の書式（構造と制約）と抽出規則を宣言する YAML ファイル。文書の frontmatter の `$schema` が指す
- **文書**: mds が検査・抽出の対象にする Markdown ファイル
- **frontmatter**: 文書の先頭にある `---` で挟んだ YAML ブロック
- **閉じた世界**: スキーマに宣言していない見出し・行を誤りとする検証の流儀。mds の既定
- **規則種別**: スキーマが文書の構造を記述するノードの種類（題名、前置部、節、項目、フィールド行、文、箇条書き、表、コードブロック）
- **ノード**: スキーマの木の1要素。検証と抽出の単位
- **フィールド行**: 行頭の空白を除いて `- 名前: 値` の形の行
- **箇条書き**: 行頭の空白を除いて `- ` で始まり `名前: 値` の形でない一覧行
- **文**: 見出しや前置部の下にある、一覧でも表でもない空でない行（散文）。リスト項目の継続段落は含まない
- **抽出**: スキーマが各ノードに `extract` で宣言する、値を取り出す規則。配置パスを持つ
- **配置パス**: `values` と `ast --schema` が値を置く場所を指すドット区切りの名前（例: `sections.context`）
- **指摘**: `check` が出す1件の結果。`{kind, severity, path, line, detail}` の形
- **停止**: 検査を行えないときに終了コード2で終わること。指摘（終了コード1）と区別する
- **基準のディレクトリ**: カレントディレクトリから上に向かって探し、最初に見つかった `.mds/` のあるディレクトリ。無ければカレントディレクトリ
- **IR**: 正規化した仕様の Markdown の文書の集まり（kotowari が検査する形式）。mds の対象例の一つ

## 範囲

作るもの:

- Rust 製の CLI `mds` と、次のコマンド
  - `mds check <path> [--format json|text] [--open]`
  - `mds values <file> [--format json|text]`
  - `mds ast <file> [--schema] [--format json]`
  - `mds --version`
- YAML スキーマ言語（文書構造の検証規則と抽出規則を記述する）
- `.mds/schemas/`（推奨のスキーマ置き場）と `.mds/cache/`（URL スキーマのキャッシュ）
- `fixtures/`: ADR と IR の書式の適用例文書と、それらを検査するスキーマ。検証とテストに使う

作らないもの:

- 文書をまたぐ整合性検査（ID の一意性、参照解決、用語集の連鎖、出典の解決、文書名の参照）。これは kotowari の領分
- 再帰的な任意深さの見出し入れ子。見出しの深さは3段（`#`、`##`、`###`）まで
- ノード間の値の一致（2つのフィールドの値が同じであること）
- 節の選択（「`## 状況` か `## 概要` のどちらか」）
- ブロック引用・水平線・画像などの行種別の制約
- 設定ファイル（`.mds/config.yaml` に相当するもの）。設定は CLI フラグとスキーマ内フラグだけ
- 抽出値の型変換（型は全部文字列）
- kotowari 本体への変更

## 要求

### R1: CLI と終了コード

コマンドは次のとおり。

```
mds check <path> [--format json|text] [--open]
mds values <file> [--format json|text]
mds ast <file> [--schema] [--format json]
mds --version
```

- `check` は `<path>` がファイルならその1文書を、ディレクトリならそのディレクトリ配下のスキーマ宣言文書をすべて検査する（R20）
- `values` の `--format` の既定は text、`check` の `--format` の既定は text
- `ast` は `--format json` のみ対応。`--format text` は引数の誤りとして停止する
- 終了コード: 0=合格、1=不合格（指摘がある）、2=停止（検査を行えない）
- `mds --version` は `mds <version>` の形（例: `mds 0.1.0`）を標準出力に出して終了コード0で終わる

- 成功の条件: `mds check` で合格の文書に終了コード0、指摘のある文書に1、読めないファイルに2が返る。`mds ast --format text` が停止になる。`mds --version` が `mds 0.1.0` の形を出力する
- 反例: 指摘があるのに終了コード0を返す。`values` の既定が json になる
- 確かめ方: 合格・不合格・停止の3つの文書で `mds check` を走らせ、終了コードを確認する。`mds ast file.md --format text` が停止することを確認する。`mds --version` の出力を確認する

### R2: frontmatter と `$schema` の解決

文書の先頭の frontmatter（`---` で挟んだ YAML ブロック）から `$schema` を読む。`$schema` 以外の frontmatter のキーは無視する。frontmatter が無い文書、または frontmatter に `$schema` キーが無い文書はスキーマを持たない。frontmatter 自体が壊れた YAML のとき、frontmatter が YAML のマッピング（キーと値の集合）でないとき、`$schema` の値が文字列でないとき（null、数値、配列など）、または `$schema` が空のときは停止する（R19）。

`$schema` の値は相対パスまたは URL。

- 相対パスは、文書の位置を基準に解決する。基準のディレクトリの特定には使わない
- URL は、初回に取得して基準のディレクトリの `.mds/cache/` に保存し、以降はキャッシュを使う。キャッシュファイル名は URL のハッシュ（SHA-256）の16進に `.yaml` を付けた名前（`<sha256hex>.yaml`）にする。キャッシュが無いまま取得できないときは停止する（R19）
- URL の取得は10秒のタイムアウトで、応答が無いときは停止する。応答のサイズは 4 MiB を上限とし、超えたら `schema_not_found` で停止する
- URL 取得に関わる失敗（タイムアウト、接続不可、サイズ超過、再取得の失敗）はすべて `schema_not_found` で停止する
- キャッシュを読んだら内容を検証し、破損・空なら URL から再取得する。再取得も失敗したら `schema_not_found` で停止する

- 成功の条件: `fixtures/adr/0001.md` が `$schema: ../.mds/schemas/adr.yaml` を宣言するとき、`fixtures/adr/.mds/schemas/adr.yaml` でなく `fixtures/.mds/schemas/adr.yaml` を読む。URL を宣言した文書で2回目の実行がキャッシュを読む。破損したキャッシュは再取得して回復する
- 反例: 文書の位置でなくカレントディレクトリ基準で相対パスを解決する。frontmatter の `title:` を誤りにする。`$schema:` が空の文書をディレクトリ検査で黙って飛ばす
- 確かめ方: 文書から離れた位置のスキーマを宣言した文書で `mds check` を走らせて通ることを確認する。frontmatter に `$schema` 以外のキーを足しても誤りにならないことを確認する。破損したキャッシュを置いて `mds check` が再取得で回復することを確認する

### R3: スキーマ言語の全体像

スキーマは YAML ファイルで、次の最上位キーを持つ。

- `name`（任意）: 型の名前。`ast --schema` の `type` に使う。無ければ `type` キーを出力しない
- `open`（任意、既定 false）: true にすると閉じた世界を緩める（R13）
- `document`: 文書の構造の木

`document` の下に置ける規則種別は次のとおり。

- `title`: 文書の題名（`# ` 見出し、深さ1）
- `preamble`: 題名の後、最初の `##` より前の前置部。フィールド行、文、箇条書きを置ける
- `sections`: 節（`## ` 見出し、深さ2）の一覧
- 節の中に置けるもの: フィールド行、文、箇条書き、表、コードブロック、項目（`### ` 見出し、深さ3）
- 項目の中に置けるもの: フィールド行、文、箇条書き

- 成功の条件: ADR のスキーマ（題名・前置部のフィールド行・節の一覧）が上記のキーだけで書ける。IR の文書単体の書式（preamble の散文、節、項目、フィールド行、表、gherkin のコードブロック）が上記のキーだけで書ける
- 反例: スキーマに宣言できないノードの種類がある。`#### ` より深い見出しを表現する手段がある
- 確かめ方: 適用例（ADR）の文書をスキーマで書き、`mds check` を通す。IR の文書単体の書式をスキーマで書いて形が合うことを確認する

### R4: 題名（title）

`title` は文書の `# ` 見出し1つを検証する。

- `pattern`: 題名の文字列が満たす正規表現。満たさないときは `title_pattern_mismatch`
- `extract`: 抽出規則（R16）

題名が無ければ `missing_title`、2つ以上あれば `multiple_titles` の誤り。

正規表現の方言は Rust の `regex` クレート（Rust regex）で、一致判定は部分一致とする（`^` と `$` を付けない限り、文字列のどこかに一致すればよい）。名前付きキャプチャは `(?<name>...)` の形。

- 成功の条件: `# ADR-0001: テストの印は \`@kotowari[ID, ...]\`` が `pattern: "^ADR-\\d{4}:"` を通り、`# テストの印は...` が `title_pattern_mismatch` になる
- 反例: 題名が2つある文書を合格にする
- 確かめ方: 題名の無い文書、題名が2つの文書、パターン不一致の文書で `mds check` を走らせる

### R5: 前置部（preamble）

`preamble` は題名の後、最初の `##` より前の前置部を検証する。次のキーを持つ。

- `fields`: 前置部のフィールド行の一覧（ADR の `- 状態:` など）
- `statement`: 前置部の文の規則（IR の「文書が扱う範囲」）
- `bullets`: 前置部の箇条書きの規則

- 成功の条件: ADR の前置部（`- 状態:`、`- 日付:`、`- 判断の記録:`）をフィールド行として検証できる。IR の前置部（散文）を文として検証できる
- 反例: 前置部にフィールド行も文も宣言できない
- 確かめ方: ADR と IR の前置部をそれぞれスキーマで書き、`mds check` を通す

### R6: 節（section）

`sections` は `## ` 見出し（深さ2）の一覧である。各節は次のキーを持つ。

- `name`: 見出しの文字列
- `required`: 出現回数の指定（R14）。既定は「ちょうど1個（必須）」
- `repeat`: 出現回数の範囲指定（R14）。`repeat` があれば `required` を上書きする
- `statement`: 節の下の文の規則
- `fields`: 節の下のフィールド行の一覧
- `bullets`: 節の下の箇条書きの規則
- `table`: 節の下の表の規則（R11）
- `codeblock`: 節の下のコードブロックの規則（R12）
- `item`: 節の下の項目（深さ3）の規則
- `extract`: 抽出規則（R16）

宣言していない見出しが現れたら `undeclared_heading` の誤り（閉じた世界。R13）。必須の節が無ければ `missing_required_section` の誤り。

- 成功の条件: ADR の `## 状況`・`## 決定`・`## 理由`・`## 却下した案`・`## 結果` を宣言し、必須・任意を検証できる
- 反例: 宣言に無い `## 補足` を誤りにしない。必須の `## 決定` が無い文書を合格にする
- 確かめ方: 宣言外の節を足した文書と、必須の節を消した文書で `mds check` を走らせる

### R7: 項目（item）

`item` は `### ID: 名前` 見出し（深さ3）を検証する。IR の `REQ-nnn` などの項目に使う。

- `id`: 見出しの ID 部分の正規表現（例: `REQ-\\d{3,}`）。ID は「見出しの先頭から `:` の直前まで」の部分。形に合わないときは `invalid_id` の誤り。見出しに `:` が無いときも `invalid_id` の誤り
- 深さが合わない見出しは `heading_level_mismatch` の誤り
- `fields`: 項目の下のフィールド行の一覧
- `statement`: 項目の下の文の規則
- `bullets`: 項目の下の箇条書きの規則
- `required`: 出現回数の指定（R14）。既定は「ちょうど1個（必須）」。`required: false` は単一値の任意
- `repeat`: 出現回数（R14）。`repeat` を宣言すると配列へ抽出する
- `extract`: 抽出規則（R16）。項目の抽出は「見出し＋本文」を1つの値にする（R16）

項目の内部のフィールド行・文・箇条書きには `extract` を宣言できない（R16）。

- 成功の条件: `### REQ-001: 印の構文` が `id: "REQ-\\d{3,}"` を通り、`### XYZ-001: 名前` が `invalid_id` になる。`#### 深すぎ` が `heading_level_mismatch` になる
- 反例: 形に合わない項目見出しを合格にする
- 確かめ方: 形の合う項目と合わない項目、深さの違う見出しをそれぞれスキーマで検証する

### R8: フィールド行（field）

フィールド行は行頭の空白を除いて `-`、`*`、`+` のいずれかのマーカーに続く `名前: 値` の形の行で、名前がスキーマが宣言したフィールド行の `name` と一致する行を指す。名前がどの宣言された `name` とも一致しない `名前: 値` の形の行は、フィールド行ではなく箇条書きとして扱う（R10）。次のキーを持つ。

- `name`: 行の名前（`- 状態: 承認済み` の「状態」）
- `required`: 出現回数の指定（R14）。既定は「ちょうど1個（必須）」
- `repeat`: 出現回数（R14）。フィールド行に `repeat` を宣言すると、同じ名前のフィールド行が複数現れ、配列へ抽出する
- `pattern`: 値の正規表現。満たさないときは `field_pattern_mismatch`
- `enum`: 値の許可リスト。含まれないときは `field_enum_invalid`
- `separator`: 値を区切る文字。指定すると値が複数に分かれる。`csv: true` は `separator: ","` の省略形。抽出時の扱いは R16
- `when`: 条件付き規則（R15）
- `extract`: 抽出規則（R16）

必須のフィールド行が無ければ `missing_required_field` の誤り。宣言していないフィールド行は `undeclared_line` の誤り（閉じた世界）。

フィールド行の継続段落（`- 名前: 値` の行の後に続く、空行で区切られたリスト項目の子である段落）は、そのフィールド行の一部として扱う。文の出現回数・規則（R9）には数えず、閉じた世界（R13）でも `undeclared_line` にしない。抽出では、フィールド行の値に継続段落を加える（R16）。空行なしの折り返し行は、値の一部として扱う（継続段落には数えない）。

`separator` と `enum` を両方指定したときは、区切った要素ごとに `enum` を照合する。`separator` と `pattern` を両方指定したときも、区切った要素ごとに `pattern` を照合する。区切った要素は前後の空白を取り除いてから照合・抽出する。区切りの結果が空の要素（`a,,b` の中間、`a,b,` の末尾）は照合の対象にし、抽出でも空文字列の要素として残す。`separator` の分割は継続段落を含めない値だけを対象にする。

フィールド行の並び順は順不同を既定とする。フィールド行の一覧に `ordered: true` を付けると、スキーマに書いた順で現れることを要求し、違反は `field_order_mismatch` の誤り。

- 成功の条件: `- 状態: 承認済み` が `enum: [承認済み, 却下, 提案中]` を通り、`- 状態: 保留` が `field_enum_invalid` になる。`- 日付: 2026-09-13` が `pattern: "^\\d{4}-\\d{2}-\\d{2}"` を通る
- 反例: `enum` に無い値を合格にする。宣言に無い `- 備考:` を誤りにしない
- 確かめ方: enum 違反、パターン違反、未宣言のフィールド行で `mds check` を走らせる

### R9: 文（statement）

文は見出しや前置部の下にある、一覧でも表でもない空でない行（散文）。リスト項目の子である継続段落（R10）は文に数えない。ブロック引用・水平線・画像などの行は文に数えない。複数行にまたがる段落は1つの文として扱い、区切りは空行とする。次のキーを持つ。

- `required`: 出現回数の指定（R14）。既定は「ちょうど1個（必須）」
- `pattern`: 文が満たす正規表現。満たさないときは `statement_pattern_mismatch`
- `enum`: 文の許可リスト。含まれないときは `statement_enum_invalid`
- `when`: 条件付き規則（R15）
- `repeat`: 出現回数（R14）
- `extract`: 抽出規則（R16）

必須の文が無ければ `missing_statement` の誤り。

- 成功の条件: `## 状況` の下に文が必須であることを宣言し、文の無い節を `missing_statement` にする
- 反例: 文の無い必須節を合格にする
- 確かめ方: 文の無い節で `mds check` を走らせる

### R10: 箇条書き（bullets）

箇条書きは行頭の空白を除いて `-`、`*`、`+` のいずれかで始まり `名前: 値` の形でない一覧行。順序付きリスト（`1. ` など数字と `.` で始まる行）は箇条書きの対象外で、閉じた世界（R13）では `undeclared_line` の誤りにする。ADR の「理由」「却下した案」の下に並ぶ行に使う。次のキーを持つ。

- `required`: 出現回数の指定（R14）。既定は「ちょうど1個（必須）」
- `pattern`: 各行が満たす正規表現。満たさないときは `bullet_pattern_mismatch`
- `when`: 条件付き規則（R15）
- `repeat`: 出現回数（R14）
- `extract`: 抽出規則（R16）。箇条書きの抽出は各行を要素にした配列になる
- `children`: 子の規則。フィールド行（`fields`）と箇条書き（`bullets`）を置ける。`bullets` は再帰的に `children` を持つことができる（任意の深さ）。項目（item）の中の箇条書きも同様に `children` を持つことができる。子の行のうち、名前が `fields` で宣言されたフィールド名と一致する `- 名前: 値` の行はフィールド行として扱い、一致しない `- 名前: 値` の行は箇条書きとして扱う（R8 の一般規則と同じ）。特定のフィールド名（`superseded_by` など）を特別扱いしない

必須の箇条書きが無ければ `missing_bullets` の誤り。

親の `bullets` の `required` / `repeat`（本数）は、トップレベルの親の箇条書きの本数だけを数える。子は親の本数には数えず、親の `children.bullets` の規則で別に数える。

`children.bullets` に `extract` を書いたとき、その抽出値は親の配置パスの下に入れる（例: 親が `extract: decisions` なら、子の箇条書きは親の値に子の行が含まれる形になる）。

リスト項目の継続段落（リスト項目の子である段落）は文ではなく、その項目の箇条書きの一部として扱う。文の出現回数・規則（R9）には数えない。`bullet` の `pattern` は元のマーカー行の行テキスト（マーカーを除いた部分）にだけ適用し、継続段落には適用しない。抽出の1要素は「元の行（マーカーとその直後の空白を含む）、継続段落、子の箇条書きの行を改行でつないだ文字列」にする。継続段落が複数のときは、継続段落どうしを空行でつないだうえで元の行と改行でつなぐ。子の箇条書きの行は、そのままのインデントで抽出要素に含める。継続段落は箇条書きの一部なので、閉じた世界（R13）でも `undeclared_line` にならない。

リスト項目の先頭がコードブロック・表のとき、その項目には元のマーカー行が無い。このとき後に続く段落は文として扱う。文の出現回数・規則（R9）の対象になり、閉じた世界（R13）では `undeclared_line` の誤りになる。

箇条書きの行は行頭の空白を除いて `-`、`*`、`+` で始まる行とする。箇条書きは任意の深さで入れ子にできる（Markdown の仕様どおり）。親の `- 名前: 値` の行の下に、子の箇条書き（さらに深い `-`、`*`、`+` の行）を置ける。子は親の一部として扱う。

- 成功の条件: ADR の「理由」の下の箇条書きを `{ min: 0 }` で宣言し、0個以上を検証できる。`extract` で各行が配列の要素になる。継続段落が文の `required` を満たさない。継続段落を含む箇条書きの `extract` が「行＋継続段落」を要素にする。入れ子の箇条書き（決定の行 + 子の `superseded_by`）を `children` で宣言し、検証・抽出できる
- 反例: 箇条書きの本数が `min` を下回る節を合格にする。継続段落を文として数えて `missing_statement` を免れる。継続段落が `bullet` の `pattern` に照合されて `bullet_pattern_mismatch` になる。`children` を宣言していないのに子の箇条書きがあるのを `undeclared_line` にしない
- 確かめ方: 本数が min を下回る節で `mds check` を走らせる。継続段落を含む文書で `statement.required: true` が `missing_statement` になることを確認する。入れ子の箇条書きを `children` で宣言して検証・抽出する

### R11: 表（table）

表は Markdown の表で、次のキーを持つ。

- `header`: ヘッダのセル列（例: `["用語", "意味", "出典"]`）。ヘッダ行が一致しないときは `table_header_mismatch`
- `required`: 出現回数の指定（R14）。既定は「ちょうど1個（必須）」
- `repeat`: 出現回数（R14）
- `extract`: 抽出規則（R16）。表の抽出はヘッダをキーにしたオブジェクトの配列になる（R16）

表が無ければ `missing_table` の誤り。列数が `header` と合わない行があるときも `table_header_mismatch` の誤り。ヘッダのセルに重複があるときは、抽出のオブジェクトで後の列が先の列を上書きする。

- 成功の条件: 用語集の表（`| 用語 | 意味 | 出典 |`）が `header: ["用語", "意味", "出典"]` を通る
- 反例: ヘッダが違う表を合格にする。列数が合わない表を合格にする
- 確かめ方: ヘッダ一致・不一致、列数一致・不一致の表で `mds check` を走らせる

### R12: コードブロック（codeblock）

コードブロックはフェンスで囲んだブロックで、次のキーを持つ。

- `lang`: 指定する言語（例: `gherkin`）。lang 指定の無いコードブロックとは区別する
- `lines`: ブロック内の行ごとの規則（例: gherkin の `Scenario:` の行のパターン）
- `required`: 出現回数の指定（R14）。既定は「ちょうど1個（必須）」
- `repeat`: 出現回数（R14）
- `extract`: 抽出規則（R16）。コードブロックの抽出はブロック全体の文字列を1つの値にする

コードブロックが無ければ `missing_codeblock`、`lang` が合わなければ `codeblock_lang_mismatch`、`lines` のパターンに合わない行があれば `codeblock_line_mismatch` の誤り。行の照合は行頭の空白を取り除いてから行い、空白のみの行（trim 後に空の行）は照合の対象外とする。

- 成功の条件: gherkin のブロックの行（タグ、`Scenario:`、ステップ）を行ごとのパターンで検証できる。空行とインデント付きの行が `codeblock_line_mismatch` にならない
- 反例: コードブロックの言語を検証できない。空行をパターンに合わない行として誤りにする
- 確かめ方: gherkin のブロックをスキーマで検証し、正しいブロックと誤った行を含むブロックで `mds check` を走らせる

### R13: 閉じた世界と `open`

閉じた世界が既定。スキーマに宣言していない見出しと行は `undeclared_heading` / `undeclared_line` の誤りにする。ただしブロック引用・水平線・画像などの行（文の対象外の行種別。R9）は、閉じた世界でも無視し、`undeclared_line` にしない。

閉じた世界は構造の内側にも及ぶ。宣言していない構造（前置部・節・項目）の内側の行も `undeclared_line` の誤りにする。`title` 規則が無いとき、`# ` 見出しは `undeclared_heading` の誤りにする。箇条書きの入れ子も同様に、親の `bullets` 規則が宣言されたとき、子は親の `children` の宣言に照合する。`children` に宣言が無い子、または親が `children` を持たないのに子リストがある場合は `undeclared_line` の誤りにする。

緩めるには2つの方法がある。

- スキーマの `open: true`（文書全体に適用）
- CLI の `--open`（`check` だけに付く。スキーマの設定を上書きする）

緩めたときは、宣言していない構造と、その内側のすべての行を許す。題名も宣言していない構造の一つであり、title 規則が無い `# ` 見出しは open では許す（閉じた世界では `undeclared_heading`）。題名より前にある見出しも open では許す（閉じた世界では `undeclared_heading`）。ただし、宣言済みの構造（題名の後の前置部・節・項目）の中に足された未宣言の構造（例: item 規則を宣言していない節の中の `### ` 項目、宣言済みの前置部の中の `### ` 見出し）は許されず、その見出しは `undeclared_heading`、その内側の行は `undeclared_line` の誤りにする。同様に、宣言済みの構造の中の未宣言の行も許されず、`undeclared_line` の誤りにする。必須の欠落や形の違反は緩めない。`--open` は緩める方向にしか働かず、スキーマが `open: true` のとき CLI で閉じた世界に戻す手段は無い。

- 成功の条件: `open: true` のスキーマで未宣言の節を足しても誤りにならない。`--open` を付けない `check` では誤りになる。`--open` を付けた `check` では誤りにならない。title 規則が無い文書の `# ` 見出しが `undeclared_heading` になる。宣言済みの節の中の未宣言の行は `open` でも `undeclared_line` になる
- 反例: `open: true` なのに必須の欠落を通す。`--open` が `values` に効く。`open` のとき未宣言の節の内側の行を `undeclared_line` にする
- 確かめ方: 開いた場合と閉じた場合で同じ文書を `mds check` し、結果が変わることを確認する。宣言済みの節の中に未宣言の行を置いて `undeclared_line` になることを確認する

### R14: 出現回数（repeat）

出現回数は `required` と `repeat` の2つの書き方がある。

- `required: true`（既定）: ちょうど1個
- `required: false`: 0個か1個（任意）
- `repeat: { min, max }`: 範囲指定。`repeat` があれば `required` を上書きする
  - `{ min: 0 }`: 0個以上
  - `{ min: 1 }`: 1個以上
  - `{ min: 0, max: 1 }`: 任意（発生回数は `required: false` と同じ。ただし抽出の形は repeat 宣言なので配列になる。R16）
  - `min` の省略は 0（`{ max: 2 }` は0個以上2個以下）
  - `max` の省略は上限なし

`min` を満たさないときは `repeat_min_not_met`、`max` を超えるときは `repeat_max_exceeded` の誤り。`min > max`、負値、非整数は `schema_invalid` の停止（R19）。繰り返すノードは配列へ抽出する（R16）。

- 成功の条件: 理由の箇条書き（0個以上）を `{ min: 0 }` で、必須のフィールド行を `required: true` で検証できる
- 反例: `{ min: 1 }` なのに空の節を合格にする。`{ max: 1 }` なのに2回現れる節を合格にする
- 確かめ方: min / max の境界をまたぐ文書で `mds check` を走らせる

### R15: 条件付き規則（when）

`when` は「あるフィールドの値に応じて、別の規則の適用を切り替える」条件節。次の形を持つ。

```yaml
when: { field: 種類, eq: algorithm }
```

- `field`: 参照するフィールド行の名前。探索は同じノードの下（同じ節・前置部・項目の中）に限定する
- `eq` / `ne`: 比較演算子。右辺はリテラル文字列のみ（別フィールド参照は不可）
- 参照するフィールドが存在しないとき、`eq` は偽、`ne` は真

`when` は `required` / `pattern` / `enum` のどれにでも添えられる。条件が真のときだけその制約が効く。YAML 上は、規則と同じ階層に `when` を並置する。

```yaml
- name: 定義
  required: true
  when: { field: 種類, eq: algorithm }
```

- 成功の条件: 「種類が algorithm のとき 定義 が必須」「種類が algorithm でないとき 文 が必須」をスキーマで書け、検証できる
- 反例: 種類が algorithm なのに 定義 が無い文書を合格にする。`when` の右辺に別のフィールド名を書ける
- 確かめ方: 条件の真・偽の両方で `mds check` を走らせる

### R16: 抽出（extract）と `values`

`extract` は4つの書式を持つ。

1. ノード全体: `extract: status` — ノードの型に応じた値。フィールド行は値（`- 状態: 承認済み` の `承認済み`。継続段落があれば、値と継続段落を改行でつなぐ。R8）、題名は題名の文字列、節・文は本文の文字列（インラインの Markdown 記法を保持し、段落は空行でつなぐ）
2. 正規表現の名前付きキャプチャ: `extract: { path: id, group: id }` — 題名の `ADR-(?<id>\d{4})` のキャプチャ `id` を取る。この書式は題名にだけ使える。題名以外のノード（フィールド行・文・箇条書き・節・項目・表・コードブロック）で宣言したときは `schema_invalid` の停止になる（R19）。題名の `title` に `pattern` が無い、または `pattern` が指定の名前付きキャプチャを含まないときも `schema_invalid` の停止になる
3. 繰り返すノード: `extract: sections.reasons` — 繰り返すノードを配列にして置く
4. 表: `extract: glossary` — ヘッダをキーにしたオブジェクトの配列にする

配置パスはドット区切りの名前で、`values` と `ast --schema` が値を置く場所を指す。`values` はパスの末端の値、`ast --schema` はパスに沿って組み立てる。

抽出値の型は全部文字列（配列はその並び）。型変換はしない。`separator` で分けた値も抽出時はそれぞれ文字列の要素になる。

`values` の出力:

- text（既定）: `キー: 値` の1行1件。ネストはパスの残りをインデント（2文字）、配列は `1.` `2.` の番号付き。1つの値に改行が含まれるときは、続きの行をそのキーより2文字深くインデントする。text は人間向けの表示であり、値の継続行とネスト行の判別が必要なら json を使う
- json: 配置パスに沿った入れ子の JSON。抽出された値だけを、配置パスをキーにして並べる。text はこの入れ子構造を行形式で表したもの

`ast --schema` の出力:

- スキーマの `name` を `type` として添えた、抽出値を配置パスで組み立てた JSON。`values` が抽出値だけを配置パスの入れ子で出すのに対し、`ast --schema` は `type` を添えて組み立てる

抽出の形は出現回数の宣言と `separator` に依存する。

- `repeat` を宣言したノードは、1件以上のときに配列へ抽出する（`{ min: 0, max: 1 }` でも1件以上なら配列）。0件のときはキーを省略する
- `repeat` が無いノードは単一値で、欠落時はキーを省略する（`required: false` は単一値）。この規則は `separator` の無いフィールド行・文・節・項目・題名・コードブロックに適用する
- `separator` を宣言したフィールド行は、repeat の有無に関わらず配列へ抽出する（各要素を文字列にした配列）。分割は継続段落を含めない値だけを対象にし、継続段落があるときは末尾の要素に `\n` を挟んで付ける。repeat と `separator` の併用は配列の配列になる。欠落時はキーを省略する（repeat と同じ規則）
- 箇条書きと表は、repeat の宣言に関わらず常に配列へ抽出する（箇条書きは行の配列、表は行オブジェクトの配列）。表に repeat を宣言しても、抽出は行オブジェクトの配列のままで入れ子にしない。複数の表・箇条書きが現れたときは、文書に現れた順で1つの配列に連結する。0件のときはキーを省略する

節の本文の抽出（書式1の「節・文は本文の文字列」）には、文（散文）と箇条書きの行だけを含める。フィールド行・表・コードブロック・項目は本文に含めず、それぞれ自分の `extract` で抽出する（フィールド行はフィールド行自身に `extract` を付けて抽出する）。本文の連結は次のとおり: 文（段落）どうしは空行でつなぐ。箇条書きの行は、R10 の抽出要素と同じ「元の行、継続段落、子の箇条書きの行を改行でつないだ文字列」を使い、要素どうしを改行で連結する。文と箇条書きの間も改行でつなぐ。子のフィールド行は親の抽出要素に含めない。子フィールドを値として抽出したい場合は、子フィールド自身に `extract` を付ける。

項目の `extract` は「見出し＋本文」を1つの値にする。ここでいう本文は、節の本文と異なり、フィールド行・文・箇条書きのすべてを含める。見出しと本文は改行でつなぎ、見出しは `### ` を付けず ID と名前だけにする。本文のフィールド行は `- 名前: 値` の行そのままを使う。本文内の連結は次のとおり: 文どうしは空行、それ以外の隣接（文と箇条書き、文とフィールド行、箇条書きどうし、フィールド行どうし、箇条書きとフィールド行）は改行でつなぐ。箇条書きの要素は R10 の抽出要素（継続段落を含む文字列）を使う。項目の内部のフィールド行・文・箇条書きには `extract` を宣言できない。宣言すると `schema_invalid` の停止になる（R19）。

`values` と `ast --schema` は検証の合否と独立に、スキーマの抽出規則に沿って文書から値を組み立てる（check と別）。ただしスキーマを解決できないとき（`$schema` が無い、スキーマが読めない）は停止する（R19）。

- 成功の条件: ADR の `values` が `{id, title, status, date, sections: {context, decision, reasons}}` を返す。表の `extract` がヘッダをキーにしたオブジェクトの配列を返す。`separator` を宣言したフィールド行が配列を返す。`ast --schema` が `name` の `type` をルートに添えて返し、`name` が無ければ `type` キーを出さない
- 反例: `values` が検証の合否で出力を変える。抽出値に日付や数値へ型変換が入る。項目内部の extract を宣言したスキーマが `schema_invalid` にならない
- 確かめ方: ADR 文書で `mds values` と `mds values --format json` を走らせ、出力を確認する。表を含む文書で表の抽出を確認する。項目内部に extract を宣言したスキーマで停止になることを確認する

### R17: 素の AST（`mds ast`）

`mds ast` は Markdown の素の構文木を JSON で出力する。mdast（unist）に準拠する。

- `{"type": "root", "children": [{"type": "heading", "depth": 1, "children": [...]}]}` の形（ルートの型は mdast 標準の `root`）
- インライン要素（テキスト、コード、強調、リンク）まで含む
- 位置情報（`position`）は出力に含めない

- 成功の条件: ADR 文書の `mds ast` が、見出し・段落・リスト・インライン要素を含む木を JSON で返す
- 反例: インライン要素がテキストのまま平坦化される
- 確かめ方: `fixtures/` の ADR 文書で `mds ast` の出力が mdast の形（`type` と `children`）に沿うことを確認する

### R18: `check` の出力と指摘の種類

`check` の出力:

- text（既定）: 指摘があるときだけ、`path:line: kind: detail` の1行1件。行番号を持たない指摘（`missing_title` など）は `path: kind: detail`。無ければ何も出さない
- json: 文書ごとの指摘をまとめた JSON。単一ファイルでもディレクトリでも同じ形。指摘が無いときも `files` の空配列を出力する
```json
{
  "files": [
    { "path": "fixtures/adr/0001.md", "findings": [...] }
  ]
}
```

指摘は `{kind, severity, path, line, detail}` の形。`severity` は `error` と `warning` の2値。v1 の指摘は全部 `error` である。`path` は文書のファイルパス（スキーマの配置パスではない）。`line` は1始まりの行番号で、行を持たない指摘は省略する。

文字コードは UTF-8。先頭の BOM は読み飛ばす。行は `\n` で数え、`\r\n` は1行に数える。最後の行に改行が無くても1行に数える。

指摘の kind は次のとおり。

- 題名: `missing_title`、`multiple_titles`、`title_pattern_mismatch`
- 閉じた世界: `undeclared_heading`、`undeclared_line`
- 必須の欠落: `missing_required_field`、`missing_required_section`、`missing_statement`、`missing_bullets`、`missing_table`、`missing_codeblock`
- 形の違反: `field_pattern_mismatch`、`field_enum_invalid`、`statement_pattern_mismatch`、`statement_enum_invalid`、`bullet_pattern_mismatch`、`heading_level_mismatch`、`invalid_id`、`field_order_mismatch`、`table_header_mismatch`、`codeblock_lang_mismatch`、`codeblock_line_mismatch`
- 繰り返し: `repeat_min_not_met`、`repeat_max_exceeded`

- 成功の条件: 不合格の文書で `check` が終了コード1を返し、text なら1行1件、json なら `files` 配列で指摘を返す。合格文書で `check --format json` が `{"files": []}` を返す
- 反例: 指摘の `severity` が `error` / `warning` 以外を取る。合格文書で `check`（text）が何かを出力する。`check --format json` が指摘ゼロで何も出力しない
- 確かめ方: 不合格文書と合格文書で `check` の text と json の出力を確認する

### R19: 停止（終了コード2）

検査を行えないときは停止する。停止理由は次のとおり。

- `schema_not_found`: 参照先のスキーマが無い、`$schema` の無い文書を `check <file>` で指定した、または URL 取得の失敗（タイムアウト、接続不可、サイズ超過、再取得の失敗）（R2）。`values` と `ast --schema` で `$schema` の無い文書やスキーマを解決できない文書を指定したときも同じ
- `schema_invalid`: スキーマの YAML が読めない、またはスキーマ言語の形に反する
- `frontmatter_invalid`: 文書の frontmatter が壊れた YAML、または `$schema` の値が文字列でない・空である（R2）。`check` / `values` / `ast --schema` のいずれでも同じ
- `unreadable_file`: 文書が読めない
- `argument_error`: 引数の誤り（知らないフラグ、`ast --format text` など）

停止は指摘（終了コード1）と区別し、終了コード2で終わる。停止の理由は標準エラーに text で1行出力する。出力の形は停止理由の kind 名に続けて説明を添える（例: `mds: schema_not_found: ...`）。

- 成功の条件: 存在しないスキーマを指す文書、壊れたスキーマ、読めないファイルのそれぞれで `check` が終了コード2を返す。`--format text` の `ast` が `argument_error` で停止する
- 反例: スキーマの欠落を指摘（終了コード1）として返す
- 確かめ方: 3つの停止例で `check` の終了コードを確認する。停止理由が標準エラーに1行出ることを確認する

### R20: ディレクトリ検査（`check ./`）

`check` がディレクトリを対象にしたとき、ディレクトリ配下の `.md` ファイルのうち frontmatter に `$schema` を持つものを検査する。スキーマを持たない文書は対象外。再帰的にサブディレクトリを辿るが、隠しディレクトリ（先頭ドット）と `.mds/` は辿らず、シンボリックリンクは辿らない。`.md` 以外の拡張子は対象外。

- json 出力は文書ごとの指摘を1つの `files` 配列にまとめる
- 1件でも指摘があれば終了コード1
- 検査中に読めないファイル、`schema_invalid` のスキーマ、`frontmatter_invalid` の文書、または `schema_not_found` の文書に出会ったときは、全体を停止（終了コード2）する。停止のときは、それまでに集めた指摘を出力せず、標準エラーに停止理由だけを1行出す

- 成功の条件: 複数の不合格文書を含むディレクトリで `check` が全文書の指摘を `files` 配列で返し、終了コード1になる。スキーマを持たない `.md` は検査されない
- 反例: スキーマを持たない文書を `missing_title` で不合格にする。隠しディレクトリを辿る。`$schema:` が空の文書を黙って飛ばす
- 確かめ方: 合格・不合格・スキーマなしの3種を含むディレクトリで `check` を走らせる。`$schema:` が空の文書を含むディレクトリで全体停止になることを確認する

## 決めていないこと

- U1 会話メモ（ChatGPT 共有リンク）の内容。取得できなかったため、依頼文だけで仕様をまとめた。メモに仕様を変える内容があれば、この仕様へ反映する
- 将来、抽出値の型付けを要求する実利用者が現れたら、スキーマに任意の `type` を足す。現時点では型は全部文字列

## 却下したもの

- REJ1 スキーマを Markdown ルール行で書く（機械検査可能な形に落とすと独自 DSL になる。YAML の方が型付きで読める）
- REJ2 文書をまたぐ整合性検査を mds に含める（責務が大きくなる。kotowari の領分）
- REJ3 抽出値の型変換（日付・数値など）を入れる（利用者の解釈を固定する。文字列が共通分母）
- REJ4 表の中身を抽出しない（IR の用語集・決定表を `values` で取れるほうが便利）
- REJ5 設定ファイル（`.mds/config.yaml`）を設ける（設定は CLI フラグとスキーマ内フラグで足りる）
