# 判断の記録: mds の仕様

## Context

mds の仕様は `docs/spec/mds.md` の散文として書かれ、実装サイクルで裁定した判断は `TODO.md` に残っていた。
仕様を kotowari の IR 形式へ写すにあたり、IR の各項目は出典として判断の記録の決定を指す必要があるが、このリポジトリには判断の記録が無かった。
そこで、既に決まっていることに番号を与えてこのファイルに集める。新しい判断はここで足さない。

A1〜A7 と A14〜A18 は仕様の成立時（2026-09-16）の判断、A8〜A11 は実装サイクルでの裁定（2026-09-17）、A12 と A13 は項目の中の表を検査するための判断（2026-09-21）を写した。
A19 と A20 は、IR の要求が指す先として必要になり、仕様の記述から起こした。

Position: 承認済み（2026-09-21）。`docs/ir/` の9文書が出典としてこのファイルの決定を指している

## Agreements

- A1 mds は、文書の frontmatter の "$schema" が指す YAML のスキーマで Markdown の文書を検査し、値を抽出する CLI にする
  - why: LLM が書いた Markdown の書式を機械的に固定できるようにするのが目的
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A2 検査の既定は閉じた世界にする。スキーマに宣言していない見出しと行を誤りにする。緩めるのはスキーマの "open" と CLI の "--open" の2つで、緩める方向にしか働かない
  - why: 書式を固定するのが目的なので、宣言していないものを黙って通すと目的を果たさない
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A3 スキーマは YAML で書く
  - why: 型付きで読める
  - rejected: スキーマを Markdown のルール行で書く（R1）
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A4 抽出した値の型は全部文字列にする。型変換はしない
  - why: 型変換は利用者の解釈を固定する。文字列が共通分母
  - rejected: 日付や数値への型変換を入れる（R3）
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A5 見出しの深さは3段（題名、節、項目）までにする。再帰的な任意深さの入れ子は持たない
  - why: 対象にする文書の形（ADR と IR）が3段で足りる。任意深さは規則と抽出の両方を複雑にする
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A6 文書をまたぐ整合性検査（ID の一意性、参照解決、用語集の連鎖、出典の解決）は持たない
  - why: 責務が大きくなる。kotowari の領分として残す
  - rejected: 文書をまたぐ整合性検査を mds に含める（R2）
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A7 設定ファイルは設けない。設定は CLI のフラグとスキーマの中のフラグで足りる
  - why: 設定の置き場が増えると、同じことを2か所で言える状態になる
  - rejected: 設定ファイル ".mds/config.yaml" を設ける（R5）
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A8 frontmatter が YAML のマッピングでないときは検査を行わずに停止する。"$schema" の値が空か空白だけのときも同じ
  - why: スキーマを解決できない以上、検査の結果は出せない。部分的な結果を出すと通ったように見える
  - decided_by: 利用者（2026-09-17 の実装サイクルでの裁定を写した）

- A9 開いた世界では、題名より前の見出しを未宣言の構造として許す。閉じた世界では誤りにする
  - why: 開いた世界は「宣言していない構造を許す」流儀であり、題名より前の見出しもその一つ
  - decided_by: 利用者（2026-09-17 の実装サイクルでの裁定を写した）

- A10 一覧のマーカー "-"、"*"、"+" は同じ扱いにする。スキーマが宣言した名前と一致すればフィールド行、一致しなければ箇条書きとして読む
  - why: Markdown ではどのマーカーも同じ一覧であり、書き手がどれを使うかで意味が変わるのは驚きになる
  - decided_by: 利用者（2026-09-17 の実装サイクルでの裁定を写した）

- A11 箇条書きの抽出の要素は、再構成せず元の行をそのまま保つ。行頭の空白とマーカーの後の空白も含める
  - why: 再構成すると、書き手が置いた空白や記法が失われ、抽出した値から元の行に戻せなくなる
  - decided_by: 利用者（2026-09-17 の実装サイクルでの裁定を写した）

- A12 項目にも表とコードブロックを宣言できるようにする。規則の中身、既定の出現回数、誤りの種類は節に宣言したときと同じにする
  - why: 見出しの下に表を持つ決定表のような項目を検査できるようにするため。節には宣言できて項目にはできないのは非対称
  - decided_by: 利用者（2026-09-21 のレビューで承認）

- A13 表の "header" は省略できるようにする。省略したときはヘッダと列数を検査せず、表の有無と出現回数だけを検査する
  - why: 表ごとにヘッダの違う表を宣言できるようにするため。コードブロックの "lang" が省略できるのと同じ扱いにそろえる
  - decided_by: 利用者（2026-09-21 のレビューで承認）

- A14 スキーマの指定は、文書からの相対パスと URL の2つを受ける。URL のスキーマは取得した内容を SHA-256 の名前でキャッシュし、壊れたキャッシュは再取得して回復する
  - why: 複数のリポジトリで同じ書式を共有するには URL が要る。毎回取得すると検査が外部に依存する
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A15 終了コードは、指摘が無いときが 0、指摘があるときが 1、検査を行えなかったときが 2 の3値にする
  - why: 「書式が違う」と「検査できなかった」は呼び出し側にとって別の事象で、同じコードにすると区別できない
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A16 出力の形は "--format" で text と json から選ぶ
  - why: 第一の利用者は LLM なので構造化された形が基本だが、人が叩く場面もある
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A17 指摘は、種類、深刻度、文書のパス、行番号、詳細の5つを持つ形にする。行を持たない指摘では行番号を省く
  - why: 機械が種類で分岐でき、人が位置をたどれる最小の組
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A18 スキーマ言語、検査、抽出のコアは CLI のフレームワークに依存しない別のクレートに置く
  - why: kotowari の中から再利用できるようにするため
  - decided_by: 利用者（仕様の成立時の判断を写した）

- A19 検査と別に、Markdown の素の構文木を mdast に沿った JSON で出す手段を持つ。位置情報は出力に含めない
  - why: スキーマで表せない調べ方をしたいときの逃げ道が要る。位置情報は木を大きくするわりに使い道が定まっていない
  - decided_by: 実装者（仕様 R17 の記述から起こした。利用者の明示の判断ではない）

- A20 スキーマの推奨の置き場は ".mds/schemas/"、URL のスキーマのキャッシュの置き場は ".mds/cache/" にする
  - why: 設定ファイルを持たない（A7）ので、置き場は規約で決める必要がある
  - decided_by: 実装者（仕様 R2 の記述から起こした。利用者の明示の判断ではない）

## Prohibitions

- P1 読めない、壊れている、形に合わない入力を黙って飛ばさない。スキーマを解決できないときと frontmatter が壊れているときは、部分的な結果を出さずに停止する
  - why: 黙って飛ばすと、検査していない文書が通ったように見える
  - decided_by: 利用者（仕様の成立時の判断を写した）

## Rejected

- R1 スキーマを Markdown のルール行で書く
  - why: 機械検査できる形に落とすと独自の DSL になる。YAML のほうが型付きで読める
  - related: A3

- R2 文書をまたぐ整合性検査を mds に含める
  - why: 責務が大きくなる。kotowari の領分
  - related: A6

- R3 抽出した値を日付や数値へ型変換する
  - why: 利用者の解釈を固定する。文字列が共通分母
  - related: A4

- R4 表の中身を抽出しない
  - why: 用語集や決定表の中身を値として取れるほうが便利
  - related: A4

- R5 設定ファイル ".mds/config.yaml" を設ける
  - why: CLI のフラグとスキーマの中のフラグで足りる
  - related: A7

- U2 項目の抽出を、配置パスをキーにしたオブジェクトにするかどうか
  - decides: 利用者。文書をまたぐ検査に項目の構造化された値が要るようになったとき
  - related: U3

- U3 抽出した値に行番号を添えるかどうか
  - decides: 利用者。U2 と同じ場面で
